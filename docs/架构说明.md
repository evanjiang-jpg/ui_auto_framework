# 架构说明

## 一、分层设计

框架按「依赖单向向下」分层，上层可依赖下层，下层绝不反向依赖：

```
               ┌──────────────┐
               │  testcases/  │  业务用例：只写业务断言
               └──────┬───────┘
                      │
               ┌──────▼───────┐
               │   pages/     │  页面对象：元素定位 + 业务动作
               └──────┬───────┘
                      │
   ┌──────────────────▼──────────────────┐
   │              common/                │  公共能力：配置/日志/上下文/接口/DB/重试/通知
   └──────────────────┬──────────────────┘
                      │
               ┌──────▼───────┐
               │   config/    │  配置与数据：环境、数据库、密钥
               └──────────────┘

   plugin/ 与 conftest.py 位于用例与 common 之间，只负责「装配」：
   把 common 与 pages 的能力以 fixture / hook 的形式注入给用例。
```

**为什么这样切**：用例层只表达业务意图；框架细节（等待、重登、截图、标签、清理）全部由
`plugin/` 与 `common/` 承担。这样业务用例改版不影响框架，框架升级也不影响用例。

## 二、pytest 钩子点（为什么要抽出来）

早期所有 fixture 和 hook 都堆在 `conftest.py` 里，加一个能力就往里塞一段，
最终 conftest 变成几百行的上帝文件，改一处怕影响全部。

现在按「钩子点」拆成四个独立模块，`conftest.py` 只声明加载它们：

```python
# conftest.py
pytest_plugins = [
    "plugin.options",           # 命令行参数、环境切换、报告头
    "plugin.fixtures",          # 全部 fixture
    "plugin.hooks_tags",        # 收集阶段：自动打 Allure 标签
    "plugin.hooks_screenshot",  # 报告阶段：失败自动截图
]
```

| 模块 | 承担的钩子 / 内容 | 职责边界 |
|---|---|---|
| `plugin/options.py` | `pytest_addoption`、`pytest_configure`、`pytest_report_header` | 只处理「参数与环境」，不碰业务 |
| `plugin/fixtures.py` | `clean_context`、`browser`、`auth`、`api_login`、`api_setup`、`db`、`db_assert` | 只做对象装配与生命周期管理 |
| `plugin/hooks_tags.py` | `pytest_collection_modifyitems` | 只做「数据 → 标签」转换 |
| `plugin/hooks_screenshot.py` | `pytest_runtest_makereport` | 只做失败现场捕获 |

**扩展新能力时的判断标准**：

- 是「提供对象给用例用」→ 放 `plugin/fixtures.py`
- 是「改变收集/执行/报告行为」→ 新建 `plugin/hooks_xxx.py` 并在 conftest 注册
- 是「与 pytest 无关的纯能力」→ 放 `common/`

## 三、fixture 的作用域设计

作用域必须从窄到宽，否则会触发 `ScopeMismatch`：

```
clean_context  (function, autouse)   每条用例前后清理上下文
db_assert      (function)  →  db      (session)
browser        (function)  →  auth    (session)
                           →  api_login(session)
```

一个关键点：**`auth` 是 session 级，不能依赖 function 级的 `browser`**。
因此 `auth` 内部自行创建一个临时 driver 完成一次登录，登录后立即关闭，只保留 token。
这样既满足「整个会话只登录一次」，又不违反作用域规则。

## 四、用例执行时序

```
pytest 启动
  └─ pytest_configure        按 --env 切换环境（plugin/options.py）
  └─ pytest_report_header    打印环境概览
  └─ 收集用例
       └─ pytest_collection_modifyitems   数据驱动自动打标签（plugin/hooks_tags.py）
  └─ 逐条执行
       ├─ clean_context 建立（清空上下文）
       ├─ 会话级 auth 首次被请求时：创建临时 driver → 登录 → 关闭 driver → 缓存 token
       ├─ browser 建立：创建 driver → 注入登录态（跳过 UI 登录）
       ├─ 用例体内执行（失败现场由 makereport 钩子捕获）
       ├─ browser 关闭 → clean_context 清理
       └─ pytest_runtest_makereport       失败则截图+源码+堆栈（plugin/hooks_screenshot.py）
  └─ 会话结束
       └─ auth 登出 → db 连接关闭
```

## 五、如何扩展

### 新增一个 fixture

```python
# plugin/fixtures.py
@pytest.fixture(scope="function")
def my_service(...):
    service = MyService(...)
    yield service
    service.close()
```

### 新增一个钩子点

```python
# plugin/hooks_mine.py
import pytest

@pytest.hookimpl(trylast=True)
def pytest_collection_modifyitems(session, config, items):
    ...
```

```python
# conftest.py 里注册
pytest_plugins = [..., "plugin.hooks_mine"]
```

### 新增一个公共能力

在 `common/` 下新建单一职责模块，供 `pages/` 或 `plugin/` 调用。

## 六、约束与注意事项

1. **项目根目录不要放 `__init__.py`**：会让 pytest 判定项目根上移，导致包导入失败
2. **钩子参数名不能改**：pluggy 要求与 hookspec 一致（如 `pytest_configure(config)`），改名会被拒绝注册
3. **pytest 小写短选项被保留**：自定义参数只能用 `--env` 这类长选项（`run.py` 对外仍提供 `-e`）
4. **Allure 标签注入必须用契约方式**：`pytest.mark.allure_label(值, label_type=类型)`，
   不能把 `allure.severity(...)` 这类装饰器当 marker 用
5. **同一文件不要并发编辑**：多人协作时注意，本框架的分层正是为降低这种冲突而设计
