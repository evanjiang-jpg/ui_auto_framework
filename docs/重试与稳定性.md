# 重试与稳定性

UI 自动化的不稳定，90% 来自两类原因：**时序问题**（元素没渲染、数据没落库、状态没流转）
和 **偶发抖动**（网络瞬断、服务短暂 5xx）。框架把治理手段分成三层，层层兜底。

---

## 一、三层稳定性治理

| 层次 | 手段 | 针对问题 | 实现 |
|---|---|---|---|
| **L1 用例内等待** | 条件轮询直到满足 | 元素/数据还没就绪 | `common/retry.py` → `wait_until` / `wait_for_value` |
| **L2 用例内重试** | 指数退避重试 | 单次操作的偶发异常 | `common/retry.py` → `retry_call` |
| **L3 用例级重跑** | 整条用例失败后重跑 | 跨步骤的整体抖动 | `@pytest.mark.flaky(reruns=N)` |

核心原则：**能等待就不要 sleep，能等待就不要重试，能重试就不要放弃**。

---

## 二、L1 条件等待（替代 sleep）

```python
from common.retry import wait_until, wait_for_value

# 等待条件成立（满足立刻返回，超时才报错）
wait_until(lambda: page.is_visible(locator), timeout=10, message="列表未加载")

# 等待某个取值变成期望值
wait_for_value(lambda: db.get_status(order_id), "paid", timeout=10)
```

为什么不用 `time.sleep(5)`：

- sleep 是**固定等待**，快的时候白等，慢的时候不够用
- 条件等待是**自适应**的，条件满足立刻返回，最坏情况才等到超时

超时会抛 `WaitTimeoutError`（继承 `AssertionError`），pytest 直接判为**失败**而非错误，
报告语义更准确。

---

## 三、L2 通用重试（指数退避）

```python
from common.retry import retry_call

result = retry_call(
    api_client.post, "/api/order",            # 被重试的函数
    json={"product_id": 1001},
    attempts=3,                                # 总尝试次数（含首次）
    delay=1.0,                                 # 首次重试等待
    backoff=2.0,                               # 退避倍数：1s → 2s → 4s
    exceptions=(ConnectionError, TimeoutError),# 只对这类异常重试
    on_retry=lambda n, e: logger.warning(f"第{n}次重试: {e}"),
)
```

要点：

- `exceptions` 收窄到**可重试的异常**，业务断言失败不要重试（重试也不会变对）
- 次数耗尽抛 `RetryExhaustedError`，携带最后一次的原始异常，便于定位
- 退避而不是固定间隔，避免把正在恢复的服务打垮

---

## 四、L3 用例级重跑

```python
@pytest.mark.flaky(reruns=2, reruns_delay=1)
@pytest.mark.p2
def test_xml_export(self, browser):
    ...
```

- 整条用例失败后自动重跑，最多 `reruns` 次
- 全部重跑仍失败才判失败
- 报告里重跑成功显示为 `RERUN → PASSED`，提示这是一条不稳定用例，值得关注

命令行统一开启（CI 常用）：

```bash
python run.py --reruns 2 --reruns-delay 1
```

## 五、重试不重复截图（重要细节）

失败自动截图由 `plugin/hooks_screenshot.py` 统一处理。如果用例要重跑 3 次，
而每次都截图，报告里就会塞满 3 张同一用例的重复截图，完全失去排查价值。

框架的判定逻辑：

```python
# 只有「后面没有重试机会」时才截图
reruns = max(命令行 --reruns, flaky marker 里的 reruns)
if execution_count <= reruns:   # 还有重试机会
    return                      # 本次不截图
```

效果：

- 首次失败、重试后成功 → **不产生截图**（这属于抖动，不是缺陷）
- 重试全部失败 → 只在**最后一次**截图，报告干净

---

## 六、失败现场三件套

用例失败时（且无重试机会）自动捕获：

1. **截图**：本地 `screenshots/` 落盘 + 内嵌 Allure
2. **页面源码**：保存为 html，便于排查元素定位问题
3. **异常堆栈**：作为文本附件挂到 Allure

用例里不需要写任何 `try/except`，全部由钩子完成，业务代码保持干净。

## 七、其它稳定性手段

| 手段 | 说明 |
|---|---|
| 显式等待替代隐式等待 | `BasePage.find/click` 内置 `WebDriverWait`，不用 `sleep` |
| 登录态复用 | 会话级只登录一次，避免每条用例都走登录流程引入波动 |
| 接口登录 | `--api-login` 跳过 UI 登录，减少一个不稳定环节 |
| 接口造数 | 前置数据走接口，避免走 UI 造数时的页面波动 |
| 用例超时保护 | `pytest-timeout` 防止个别用例卡死拖垮整轮 |
| 单条用例上下文隔离 | `clean_context` 自动清理，避免参数串扰导致的偶发失败 |

## 八、标签规范

标签在 `pytest.ini` 注册，`--strict-markers` 下未注册的标签会直接报错，防止写错名字。

### 四个维度

| 维度 | 标签 | 用途 |
|---|---|---|
| **执行层级** | `smoke` / `p0` / `p1` / `p2` | CI 分层执行：冒烟卡点、高优回归、全量 |
| **业务模块** | `login` / `order` / `user` / `payment` / `search` | 按模块筛选、定位责任人 |
| **用例类型** | `ui` / `api` / `db` / `regression` | 区分用例性质 |
| **执行特征** | `slow` / `flaky` / `skip_ci` | 控制执行策略 |

### 使用规范

1. 每条用例**至少**打 1 个执行层级标签 + 1 个业务模块标签
2. `@pytest.mark.skip_ci`：需要真人介入（验证码、扫码）的用例，CI 模式下自动排除
3. `@pytest.mark.flaky(reruns=N)`：已知偶发的用例，配合重跑
4. `@pytest.mark.slow`：耗时长，冒烟与 P0 默认不带，只在全量回归带上

### 组合使用

```bash
python run.py -m "smoke and p0"            # 冒烟且高优
python run.py -m "p0 and not slow"         # 排除慢用例
python run.py -m "regression and db"       # 回归里的数据库断言用例
python run.py --list-markers               # 查看全部标签
```

### CI 分层执行建议

| 触发场景 | 执行范围 |
|---|---|
| MR / 合入主干 | `smoke`（必须全过，卡点） |
| 打 tag / 手动触发 | `p0` |
| 夜间定时 / 全量回归 | `p0 or p1` |
