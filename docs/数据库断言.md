# 数据库断言

UI 自动化只校验页面文字是不够的：页面提示「保存成功」，数据库里可能根本没写入。
数据库断言用于从**数据层**验证操作结果，比 UI 文案可靠得多。

---

## 一、配置

`config/database.yaml` 按环境分层，规则与主配置一致（default + 环境层 + 本地覆盖）：

```yaml
default:
  type: sqlite                            # sqlite / mysql / postgresql
  database: data/demo.db
  readonly: false
  timeout: 10

test:
  type: mysql
  host: test-db.internal
  port: 3306
  user: tester
  password: "${DB_PASSWORD}"              # 从环境变量注入，不留明文
  database: test_db
  charset: utf8mb4
  readonly: true                          # 测试/生产建议只读，防止误改数据
```

支持的数据库类型与依赖：

| type | 驱动 | 安装 |
|---|---|---|
| `sqlite` | Python 内置 | 无需安装（默认，适合本地/demo） |
| `mysql` | pymysql | `pip install pymysql` |
| `postgresql` | psycopg2 | `pip install psycopg2-binary` |

**只读保护**：`readonly: true` 时任何写操作都会抛 `PermissionError`，防止测试误改线上数据。

---

## 二、两个 fixture

```python
def test_xxx(self, db, db_assert):
    ...
```

- `db`（session 级）：数据库连接客户端 `DatabaseClient`，会话结束自动关闭。
  sqlite 模式下会自动执行 `data/schema.sql` 建表与种子数据，可重复执行（幂等）。
- `db_assert`（function 级）：断言器 `DatabaseAsserter`，封装了常用断言。

---

## 三、断言 API

### 立即断言（查不到就失败）

| 方法 | 说明 |
|---|---|
| `assert_row_exists(table, where)` | 断言存在符合条件的记录，返回该行 |
| `assert_row_not_exists(table, where)` | 断言不存在符合条件的记录 |
| `assert_row_count(table, expected, where)` | 断言记录数 |
| `assert_column_value(table, column, expected, where)` | 断言某行某列的值 |

```python
db_assert.assert_row_exists("users", {"username": "demo_user"})
db_assert.assert_column_value("users", "status", "active", {"username": "demo_user"})
db_assert.assert_row_count("orders", 1, {"user_id": 1})
```

### 轮询等待（专治异步最终一致）

UI 提示成功但数据异步落库时，立即断言会失败。用等待类断言，超时才失败：

| 方法 | 说明 |
|---|---|
| `wait_for_row(table, where, timeout)` | 等待记录出现 |
| `wait_for_column_value(table, column, expected, where, timeout)` | 等待某列变成期望值（如订单状态流转） |
| `wait_for_count(table, expected, where, timeout)` | 等待记录数达到期望 |

```python
# 下单后订单状态由「待支付」异步流转为「已支付」
db_assert.wait_for_column_value("orders", "status", "paid",
                                where={"user_id": user_id}, timeout=10)
```

所有 `where` 条件一律**参数化绑定**，无需手拼 SQL 字符串，避免注入与拼写错误。

## 四、直接查询

`db` fixture 也提供直接查询能力，便于调试或做复杂校验：

```python
rows = db.query("SELECT * FROM orders WHERE user_id = ? AND amount > ?", [user_id, 100])
row = db.query_one("SELECT * FROM users WHERE username = ?", ["demo_user"])
count = db.count("orders", {"status": "paid"})
value = db.query_value("SELECT COUNT(*) FROM users")
affected = db.execute("UPDATE users SET status = ? WHERE id = ?", ["frozen", 1])
```

> 上层 SQL 统一写 `?` 占位符，框架会按数据库类型自动适配（mysql/pg 转成 `%s`）。

## 六、最佳实践

1. **UI 断言 + DB 断言组合**：页面校验交互正确性，数据库校验数据落库正确性
2. **测试数据自造自清**：用例内创建的数据在 `finally` 里删掉，避免污染环境
3. **异步用等待不用 sleep**：`wait_for_*` 条件满足立即返回，比固定 sleep 既快又稳
4. **生产/预发布一律 readonly**：只允许查询，从机制上杜绝误改
5. **断言失败信息要能定位**：断言方法都会输出表名、条件、期望值与实际值
